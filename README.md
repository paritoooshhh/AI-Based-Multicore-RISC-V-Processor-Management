# AI-Based Multicore RISC-V Processor Management

An experimental hardware-software project that combines a **32-bit RISC-V processor implemented in Verilog**, RTL simulation, workload benchmarking, and a **Random Forest model for deadline-aware core selection**.

The project explores how workload size, workload characteristics, and execution deadlines can guide the allocation of 1–4 processor cores. The goal is to investigate how smaller workloads can use fewer cores while larger or more time-sensitive workloads can receive additional computing resources.

## Key Highlights

- **32-bit RISC-V RTL:** Processor components, instruction execution, and performance counters.
- **RTL verification:** Testbenches using Icarus Verilog for arithmetic, memory, branch, and edge-case behavior.
- **144 benchmark configurations:** Four workload families, nine workload sizes, and four requested core counts.
- **Machine learning:** Random Forest classifier built with Python and scikit-learn.
- **75% classification accuracy:** The model matched 36 of 48 held-out, policy-generated core-selection labels.
- **Deadline-aware allocation:** Core-selection decisions consider execution deadlines and assumed power costs.
- **Matrix multiplication UI:** Integration for exploring matrix-multiplication workloads and project outputs.

> **Important:** This is an experimental policy-imitation project. The reported accuracy measures agreement with labels generated by the project's scheduling policy. It does not establish globally optimal scheduling, physical hardware speedups, or measured energy savings.

## Project Overview

Allocating more processor cores can reduce execution time for some workloads, but assigning extra cores to small workloads may be unnecessary. This project investigates a workload-aware approach to selecting the number of cores.

The system follows this workflow:

1. **Verify the processor RTL:** Exercise instruction behavior and relevant edge cases using testbenches.
2. **Benchmark workloads:** Simulate different workload families, sizes, and core counts.
3. **Generate scheduling labels:** Apply a deadline-aware policy to determine the preferred core count for each workload and deadline ratio.
4. **Train the classifier:** Use benchmark features and policy-generated labels to train a Random Forest model.
5. **Evaluate predictions:** Compare predicted core counts with the policy-generated labels on held-out examples.
6. **Inspect results:** Review simulation logs, benchmark metrics, model outputs, and evaluation reports.

## System Architecture

The project combines three main components.

### 1. RISC-V RTL and Verification

The RTL describes the processor and its associated workload and multicore components.

The testbenches exercise instruction behavior and inspect outputs and activity counters, including:

- Arithmetic and ALU operations
- Register-file behavior and instruction execution
- Memory loads and stores
- Branch instructions and taken branches
- Execution cycles and instruction counts
- Edge cases and multicore workload behavior

Icarus Verilog is used to compile and simulate the RTL testbenches.

### 2. Benchmark Data Generation

The heavy-workload benchmark covers four workload families:

- Arithmetic
- Branch-heavy
- Memory-heavy
- Mixed

The benchmark uses nine workload sizes:

`8, 16, 32, 48, 64, 96, 128, 192, 256`

Each workload-size combination is evaluated with requested core counts of 1, 2, 3, and 4.

This gives:

**4 workload types × 9 sizes × 4 core counts = 144 configurations**

The expected benchmark CSV is:

`data/heavy_workload_dataset_144.csv`

The dataset includes workload characteristics, requested core count, elapsed cycles, result correctness, instruction counts, and relevant activity counters.

### 3. Deadline-Aware Core Selection

The scheduling model uses a Random Forest classifier implemented with Python and scikit-learn.

The training pipeline:

- Validates the benchmark dataset.
- Generates supervised examples for deadline ratios of `0.90`, `0.75`, `0.50`, and `0.30`.
- Uses one-core elapsed cycles as the baseline for each workload and size.
- Applies a deadline-aware policy using execution-cycle information and assumed power costs.
- One-hot encodes workload type and standardizes numeric features.
- Trains a `RandomForestClassifier` with 300 trees and `random_state=42`.
- Evaluates predictions on held-out examples.
- Trains a final deployment candidate using all generated examples.

The model artifact is intended to support workload-aware core-selection experiments rather than claim an optimal scheduling solution.

## Results and Analysis

### 1. Core Count vs. Average RTL Benchmark Cycles

The mixed-workload benchmark shows average elapsed cycles decreasing from approximately 845 cycles with one core to approximately 215 cycles with four cores.

Fewer cycles indicate less simulated execution time in this benchmark. The results illustrate the potential performance benefit of increasing the requested core count for the tested mixed workload.

Actual performance depends on the workload and the behavior represented by the RTL simulation.

### 2. Workload Size vs. RTL Cycles

The benchmark shows that increasing workload size increases execution cycles across the tested core counts. The differences between core counts become more pronounced for larger workloads.

This motivates workload-aware allocation:

- **Smaller workloads:** Consider fewer cores to avoid unnecessary resource allocation.
- **Larger workloads:** Consider additional cores when they can reduce execution cycles.
- **Deadline-constrained workloads:** Select the core count according to the deadline-aware policy.

The purpose is to investigate a balance between execution performance and resource utilization rather than always selecting the maximum number of cores.

### 3. Deadline Ratio vs. Policy-Generated Core Selections

The scheduling policy generates different core-selection labels under different deadline constraints.

In the benchmark, relaxed deadlines can permit lower core counts, while tighter deadlines can favor additional cores to satisfy the execution-time requirement.

The deadline ratio represents the target deadline relative to the one-core baseline. These policy decisions depend on the project's assumptions and benchmark data.

### 4. Random Forest Evaluation

The reported held-out evaluation achieved **75% accuracy, correctly matching 36 of 48 policy-generated labels**.

This indicates that the classifier reproduced the scheduling policy's decisions for 36 evaluated examples.

The remaining predictions did not match the generated labels. Further evaluation is needed to understand the types of workloads where predictions differ and whether the model generalizes to additional workload sizes and configurations.

**Interpretation note:** The labels are generated by a heuristic scheduling policy, not by a proven optimal scheduler. Consequently, 75% accuracy is a measure of policy agreement, not a direct measure of energy efficiency or hardware performance improvement.

## Power Model and Limitations

The scheduler uses an assumed power cost of `0.325 W` per core, scaled linearly for core counts from 1 to 4.

These values are modeling assumptions, not physical measurements from a fabricated processor or a hardware power-analysis flow.

Current limitations include:

- The model learns from policy-generated labels.
- The assumed power costs are not measured hardware power.
- RTL benchmark cycles do not establish real-world processor speedup.
- Held-out workload-size evaluation does not guarantee generalization to arbitrary workloads.
- Model predictions require separate validation before being used in an actual processor scheduler.

The project is an experimental study of workload-aware core allocation and the use of machine learning to reproduce scheduling decisions.

## Requirements

- Windows PowerShell
- Python 3
- Icarus Verilog (`iverilog` and `vvp`)
- Python packages:
  - `pandas`
  - `scikit-learn`
  - `joblib`

## Setup and Execution

Run the following commands from the repository root in Windows PowerShell.

### 1. Check the required tools

```powershell
python --version
iverilog -V
vvp -V
```

Ensure Python and Icarus Verilog are installed and available on your `PATH`.

### 2. Install Python dependencies

```powershell
python -m pip install pandas scikit-learn joblib
```

### 3. Run the RTL testbenches

```powershell
.\run_all_testbenches.ps1
```

If PowerShell blocks the script because of the execution policy, you can allow it for the current process:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\run_all_testbenches.ps1
```

Review the generated logs to identify compilation errors, failed assertions, or simulation issues.

### 4. Prepare the benchmark dataset

Ensure the completed CSV exists at:

```text
data/heavy_workload_dataset_144.csv
```

The training script expects exactly 144 valid configurations and the required dataset columns. If the dataset is missing or has an unexpected structure, check the dataset-generation workflow and CSV path before proceeding.

### 5. Train and evaluate the scheduler

```powershell
python .\train_deadline_core_scheduler_144.py
```

The script is configured to produce:

```text
ml/models/deadline_core_scheduler_144.joblib
ml/deadline_scheduler_144_report.txt
ml/deadline_scheduler_examples_144.csv
```

It writes the expanded model as a separate artifact rather than overwriting a different original model.

### 6. Evaluate unseen workload sizes

```powershell
python .\evaluate_unseen_workload_sizes.py
```

Check the script's inputs and options if your local version has been customized.

## Troubleshooting

**PowerShell reports that `/usr/bin/env` is not recognized**

Use the Windows Python command:

```powershell
python script_name.py
```

**An RTL module cannot be found during compilation**

Check that the source file defining the module is included in the compile command.

**Duplicate module declarations appear**

Ensure that two source files defining the same module are not compiled together. Use the intended RTL implementation.

**The benchmark dataset is missing**

Verify the CSV path relative to the repository root and run the appropriate data-generation workflow.

**Dataset validation fails**

Check the row count, required columns, result-correctness values, and coverage of core counts 1–4 for every expected workload and size.

**Python reports missing packages**

Install the required dependencies in the same Python environment used to execute the scripts.
